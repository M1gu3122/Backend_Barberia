# GUÍA DE GIT PARA TRABAJAR EN EQUIPO

## Proyecto de Barbería

Esta guía explica el flujo que debemos seguir para trabajar varios desarrolladores en el mismo proyecto sin sobrescribir el trabajo de los demás.

---

# 1. ¿Cómo vamos a trabajar?

En el proyecto tendremos una rama principal:

```text
main
```

La rama `main` debe contener siempre una versión estable del proyecto.

Cada integrante trabajará sus funcionalidades en una rama independiente:

```text
main
│
├── feature/citas
├── feature/servicios
├── feature/login
├── feature/barberos
└── fix/validacion-citas
```

### ¿Por qué usamos ramas?

Porque así cada persona puede trabajar en su funcionalidad sin modificar directamente la versión principal.

Por ejemplo:

```text
Miguel → feature/barberos
Carlos → feature/citas
Andrés → feature/login
```

Cada uno trabaja independientemente y posteriormente su código se integra a `main` mediante un **Pull Request**.

---

# 2. ¿Cuándo debo crear una nueva rama?

Debes crear una nueva rama **cada vez que vayas a desarrollar una nueva funcionalidad, corrección o tarea**.

Por ejemplo:

* Crear módulo de citas → `feature/citas`
* Crear módulo de servicios → `feature/servicios`
* Crear login → `feature/login`
* Crear módulo de barberos → `feature/barberos`
* Corregir validación → `fix/validacion-citas`
* Corregir un error visual → `fix/error-interfaz`

### No hagas esto:

```text
main
↓
Trabajar directamente aquí
↓
git add .
git commit
git push
```

### Haz esto:

```text
main
↓
Actualizar main
↓
Crear una rama
↓
Trabajar en la rama
↓
Commit
↓
Push
↓
Pull Request
↓
Merge → main
```

---

# 3. Antes de comenzar cualquier tarea

Primero debemos asegurarnos de tener la versión más reciente de `main`.

Ejecuta:

```bash
git switch main
```

Luego:

```bash
git pull origin main
```

Esto descarga los cambios que otros compañeros hayan integrado a `main`.

### IMPORTANTE

**Siempre actualiza `main` antes de crear una nueva rama.**

Así tu nueva rama comenzará desde la versión más reciente del proyecto.

---

# 4. Crear una nueva rama

Supongamos que te asignaron desarrollar el módulo de citas.

Primero:

```bash
git switch main
```

Actualizas:

```bash
git pull origin main
```

Luego creas la rama:

```bash
git switch -c feature/citas
```

Este comando hace dos cosas:

1. Crea la rama `feature/citas`.
2. Cambia automáticamente a esa rama.

Puedes comprobarlo con:

```bash
git branch
```

Verás algo parecido a:

```text
* feature/citas
  main
```

El `*` indica la rama en la que estás trabajando actualmente.

---

# 5. ¿Qué nombre debe tener la rama?

Utilizaremos esta estructura:

```text
feature/nombre-de-la-funcionalidad
```

Para funcionalidades nuevas:

```text
feature/citas
feature/login
feature/barberos
feature/servicios
```

Para correcciones:

```text
fix/validacion-citas
fix/error-login
fix/calculo-total
```

Para documentación:

```text
docs/documentacion-api
```

---

# 6. Trabajar en la nueva rama

Una vez creada la rama puedes modificar el código normalmente.

Por ejemplo:

```text
feature/barberos
```

Puedes:

* Crear archivos.
* Modificar archivos.
* Eliminar archivos.
* Probar la funcionalidad.
* Ejecutar el proyecto.

Todos estos cambios permanecerán en tu rama.

---

# 7. Revisar qué cambió

Antes de hacer un commit utiliza:

```bash
git status
```

Git mostrará los archivos modificados.

También puedes revisar exactamente qué cambiaste:

```bash
git diff
```

Esto es recomendable antes de guardar los cambios.

---

# 8. Guardar los cambios con un commit

Cuando hayas terminado una parte de tu trabajo:

```bash
git add .
```

Luego:

```bash
git commit -m "feat: agrega modulo de barberos"
```

### Ejemplos de commits

Nueva funcionalidad:

```bash
git commit -m "feat: agrega rutas para servicios"
```

Corrección:

```bash
git commit -m "fix: corrige validacion de citas"
```

Documentación:

```bash
git commit -m "docs: agrega documentacion de API"
```

Reorganización:

```bash
git commit -m "refactor: reorganiza repositorios"
```

### Recomendación

Los commits deben describir claramente lo que hiciste.

Evita:

```bash
git commit -m "cambios"
git commit -m "arreglado"
git commit -m "cosas nuevas"
```

Es mejor:

```bash
git commit -m "feat: agrega formulario de barberos"
```

---

# 9. Subir la rama a GitHub

La primera vez que subas una rama debes utilizar:

```bash
git push -u origin feature/barberos
```

Después de haber configurado la rama, normalmente bastará con:

```bash
git push
```

Tu rama aparecerá en GitHub:

```text
main
feature/barberos
```

---

# 10. Crear un Pull Request

Una vez que hayas terminado tu tarea, debes crear un **Pull Request (PR)**.

El PR debe ir:

```text
feature/barberos
        ↓
       main
```

Es decir:

> "Quiero integrar los cambios de mi rama `feature/barberos` en `main`."

Los demás integrantes pueden revisar tu código antes de hacer el Merge.

---

# 11. Después del Merge

Cuando el Pull Request haya sido aceptado y se haya hecho Merge a `main`, tu trabajo ya estará integrado.

Ahora debes actualizar tu `main` local.

Primero:

```bash
git switch main
```

Después:

```bash
git pull origin main
```

Ahora tu computadora tiene la versión actualizada del proyecto.

---

# 12. ¿Qué hago con mi rama después del Merge?

Una vez que la funcionalidad ya fue integrada a `main`, la rama ya no es necesaria.

Puedes eliminarla localmente:

```bash
git branch -d feature/barberos
```

Y eliminarla de GitHub:

```bash
git push origin --delete feature/barberos
```

Después, cuando tengas una nueva tarea, **no reutilices la rama anterior**.

Crea una nueva:

```bash
git switch main
git pull origin main
git switch -c feature/nueva-tarea
```

---

# 13. FLUJO COMPLETO PARA UNA NUEVA TAREA

Cada vez que recibas una tarea nueva debes seguir este proceso:

## Paso 1 — Ir a main

```bash
git switch main
```

## Paso 2 — Actualizar main

```bash
git pull origin main
```

## Paso 3 — Crear una nueva rama

Ejemplo:

```bash
git switch -c feature/citas
```

## Paso 4 — Trabajar

Realiza todos los cambios necesarios.

## Paso 5 — Revisar

```bash
git status
```

Opcionalmente:

```bash
git diff
```

## Paso 6 — Agregar cambios

```bash
git add .
```

## Paso 7 — Crear commit

```bash
git commit -m "feat: agrega modulo de citas"
```

## Paso 8 — Subir la rama

```bash
git push -u origin feature/citas
```

## Paso 9 — Crear Pull Request

En GitHub:

```text
feature/citas → main
```

## Paso 10 — Revisión

El equipo revisa el código.

## Paso 11 — Merge

Si todo está correcto, se integra el Pull Request.

## Paso 12 — Actualizar main

Después del Merge:

```bash
git switch main
git pull origin main
```

## Paso 13 — Eliminar la rama

```bash
git branch -d feature/citas
```

---

# 14. ¿Qué pasa si ya existe una rama para mi tarea?

Antes de crear una rama nueva puedes comprobar las ramas disponibles:

```bash
git branch
```

Para ver también las ramas que existen en GitHub:

```bash
git branch -a
```

Si ya existe:

```text
feature/citas
```

**NO debes crear otra rama con el mismo nombre.**

Si esa rama es tuya y quieres continuar trabajando:

```bash
git switch feature/citas
```

Luego puedes actualizarla según el flujo que esté utilizando el equipo.

---

# 15. ¿Qué pasa si otro compañero está trabajando en la misma funcionalidad?

Lo ideal es **no trabajar dos personas en la misma rama**.

Por ejemplo:

```text
Carlos → feature/citas
Miguel → feature/servicios
Andrés → feature/login
```

Si dos personas necesitan trabajar en la misma funcionalidad, deben coordinarse.

Una posibilidad es dividir la tarea:

```text
feature/citas-backend
feature/citas-frontend
```

De esta manera se reduce la posibilidad de conflictos.

---

# 16. ¿Qué pasa si Git me dice "fetch first"?

Por ejemplo:

```text
! [rejected] main -> main (fetch first)
```

Significa que GitHub tiene cambios que tu computadora todavía no tiene.

Primero:

```bash
git fetch origin
```

Puedes comprobar los commits que están en GitHub y no tienes localmente:

```bash
git log main..origin/main --oneline
```

Y los commits que tienes localmente y todavía no están en GitHub:

```bash
git log origin/main..main --oneline
```

**No utilices `git push --force` sin saber exactamente qué estás haciendo.**

---

# 17. Conflictos de Git

Puede ocurrir que dos personas modifiquen las mismas líneas de un archivo.

Por ejemplo:

```text
Miguel → src/routers/cita.py
Carlos → src/routers/cita.py
```

Si ambos modifican la misma parte, Git puede mostrar:

```text
CONFLICT (content): Merge conflict in src/routers/cita.py
```

Esto **NO significa que el proyecto se haya perdido**.

Git está indicando que necesita que decidamos qué cambios conservar.

El archivo puede mostrar algo parecido a:

```text
<<<<<<< HEAD
Código de Miguel
=======
Código de Carlos
>>>>>>> otra-rama
```

Debemos editar el archivo y decidir qué código debe permanecer.

Después:

```bash
git add .
```

Y continuar con el proceso correspondiente.

**Si no entiendes un conflicto, no ejecutes comandos destructivos. Pide ayuda antes de continuar.**

---

# 18. Reglas importantes del equipo

### Regla 1

**No trabajar directamente sobre `main`.**

### Regla 2

**Crear una rama nueva para cada tarea.**

### Regla 3

Antes de crear una rama:

```bash
git switch main
git pull origin main
```

### Regla 4

Utilizar nombres descriptivos para las ramas.

### Regla 5

Hacer commits pequeños y descriptivos.

### Regla 6

Subir las ramas a GitHub.

### Regla 7

Utilizar Pull Requests para integrar cambios a `main`.

### Regla 8

Revisar el código antes de hacer Merge.

### Regla 9

Después de un Merge, actualizar `main`:

```bash
git switch main
git pull origin main
```

### Regla 10

No utilizar comandos destructivos sin entenderlos.

Especialmente:

```bash
git reset --hard
git push --force
```

### Regla 11

**Nunca subir información sensible al repositorio.**

No subir:

```text
.env
contraseñas
tokens
API keys
credenciales
claves privadas
```

Utilizar `.gitignore` para evitar subir estos archivos accidentalmente.

# 21. RESUMEN: ¿QUÉ HAGO CADA VEZ QUE ME ASIGNAN UNA TAREA?

Memoriza este flujo:

```text
        ┌─────────────────┐
        │   Nueva tarea   │
        └────────┬────────┘
                 ↓
        git switch main
                 ↓
        git pull origin main
                 ↓
    git switch -c feature/tarea
                 ↓
          Trabajar código
                 ↓
           git status
                 ↓
            git add .
                 ↓
       git commit -m "feat: ..."
                 ↓
       git push -u origin
       feature/tarea
                 ↓
       Crear Pull Request
                 ↓
          Revisión equipo
                 ↓
              MERGE
                 ↓
        git switch main
                 ↓
        git pull origin main
                 ↓
        Nueva tarea → repetir
```

## REGLA DE ORO

**Nunca empieces una tarea nueva trabajando directamente sobre `main`.**

Siempre:

```bash
git switch main
git pull origin main
git switch -c feature/nueva-tarea
```

Y cuando termines:

```text
Rama → Push → Pull Request → Revisión → Merge → Actualizar main
```

Ese será el flujo estándar para trabajar en equipo en el proyecto de Barbería.
